# Track Specification: 租户隔离配套工作及登录逻辑改造

## 概述
本 Track 旨在完善系统的多租户隔离机制。核心工作包括：数据库模型补全、登录逻辑改造（支持 `用户名@租户代码` 且兼容单租户模式）、多租户开关配置，以及超级管理员的平台管理与租户切换功能。

## 功能要求

### 1. 数据库与模型补全
- 检查后端业务模型和数据库表，补全 `tenant_id` 字段。
- 在 `tenant` 表中增加 `code` (租户代码) 字段，并确保其唯一性。

### 2. 登录逻辑改造
- **格式支持**: 模式开启时支持 `用户名@租户代码` (例如 `admin@system`, `jack@ACompanyCode`)。
- **用户名复用**: 允许不同租户下存在相同的用户名。
- **单租户兼容 (核心)**: 
  - 当 `multiTenant` 开关关闭时，登录不需要 `@租户代码` 后缀。
  - 系统自动将此类登录关联到默认租户（ID: 1）。
- **系统租户**: 预设 `system` 租户用于存放平台超级管理员。

### 3. 多租户模式开关
- **全局配置**: `config.toml` 中增加 `app.multiTenant` 开关。
- **默认租户**: 当开关为 `false` 时，所有业务操作和查询默认使用 `tenant_id = 1`。

### 4. 超级管理员与身份切换
- **租户身份切换**: 超管通过切换接口获得目标租户的 JWT Token，实现“变身”操作。

## 非功能要求
- **向下兼容**: 确保现有的单租户用户在配置正确的情况下仍能正常使用。
- **安全性**: 严格校验切换租户身份的权限，仅允许超级管理员执行此操作。

## 验收标准
- [ ] 支持 `A@A` 和 `A@B` 登录不同租户下的同名账户。
- [ ] 关闭多租户开关后，使用 `admin` 即可直接登录并关联到租户 1。
- [ ] 所有业务表操作在单租户模式下均能自动填充 `tenant_id = 1`。

## 超出范围
- 本 Track 不涉及前端 UI 的最终美化，仅实现核心交互逻辑和接口调用。
- 不涉及跨租户的数据迁移工具。
