# 消息中心功能需求规范 (spec.md)

## 1. 概述 (Overview)
为系统添加统一的消息中心模块，汇总各业务模块的消息。支持实时推送、异步处理、多终端通知预留及灵活的业务跳转功能，提升系统的交互体验与业务协同效率。

## 2. 功能需求 (Functional Requirements)

### 2.1 消息分类与存储
- **消息类型支持**：
    - **系统公告 (System Notice)**：管理员发布的全局消息。
    - **业务通知 (Business Notification)**：由业务逻辑触发的通知（如审批通过）。
    - **待办任务 (Todo/Task)**：需要用户处理的动作，支持状态联动。
- **状态管理**：
    - 采用 **已读关联表模式 (Read Mapping)**：消息体单份存储，通过关联表记录用户的已读状态，降低冗余。
    - 支持“一键已读”功能。

### 2.2 实时推送机制
- **技术实现**：基于 **WebSocket** 实现服务端向前端的实时推送。
- **功能点**：
    - 客户端登录后自动建立连接。
    - 收到消息时，前端右上角实时弹出提醒。
    - 自动更新未读消息计数。

### 2.3 业务跳转与交互
- **跳转配置**：支持 **路由路径 (Path) + 业务参数 (Params/Object ID)** 的组合方案。
- **场景覆盖**：
    - 直接跳转至业务列表页。
    - 跳转至详情页。
    - 预留前端处理逻辑，支持在当前页打开特定功能弹窗。

### 2.4 异步处理机制
- **技术实现**：利用 **Redis (Streams/PubSub)** 作为异步中转层。
- **扩展性**：业务模块将消息推入 Redis，由专用消费者处理 WebSocket 推送，并预留后续接入 **短信 (SMS)** 和 **邮件 (Email)** 通知服务的接口。

## 3. 非功能需求 (Non-Functional Requirements)
- **高性能**：后端利用 Go 协程高效处理大量并发连接。
- **低耦合**：业务模块仅需调用统一的消息发送接口，不直接依赖推送逻辑。
- **易扩展**：消息体采用 JSON 格式存储业务参数，方便前端动态解析。

## 4. 验收标准 (Acceptance Criteria)
1. 成功建立 WebSocket 连接，且在多标签页下能正常接收推送。
2. 发布系统公告后，所有在线用户能实时收到通知。
3. 点击消息通知能正确跳转至预设的业务页面或打开详情。
4. 消息标记为已读后，未读数实时更新。
5. 验证异步机制：模拟高频发送消息，系统响应不受影响。

## 5. 超出范围 (Out of Scope)
- 本阶段暂不实现具体的短信和邮件发送对接（仅保留接口与异步逻辑）。
- 不包含复杂的历史消息全文搜索功能。
